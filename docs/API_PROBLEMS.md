# API problems found

> Source: the OpenAPI spec of spring-petclinic-rest (`src/main/resources/openapi.yml`, master) cross-checked with the README. Items marked ⚠ depend on the build you run — confirm in Swagger UI (`/petclinic/swagger-ui.html`) before the interview.

| #   | Problem                                                                                                                                                                                                                                              | Workaround                                                                       | Proposed API change                                                                          |
| --- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| 1   | `GET /owners` is **unpaginated** and every owner embeds _all_ pets and _all_ visits → payload grows with the clinic. ⚠ The spec also has a paginated `GET /v2/owners?page&size&lastName` (max 100/page), which the provided README does not mention. | Fetch once, cache, search locally; render ≤50 rows                               | Use `/v2` once it is the stable contract; add a lightweight owner summary (no nested visits) |
| 2   | Search is only `?lastName=` — no first name, phone, city or pet.                                                                                                                                                                                     | **Local search** over the cached list (see above)                                | `GET /owners?q=` over name/phone/city/pet, with pagination                                   |
| 3   | Validation is strict for real-world data: phone digits-only (≤20, so no `+`, spaces, dashes), names letters-only with ≤3 words and ≤30 chars (no digits, no `Dr.` prefix)                                                                            | Same rules in the form, with clear messages; receptionist must normalise numbers | Accept E.164 / free-form phone, looser name rules                                            |
| 4   | Visit has only a **date** (no time, vet or status), so same-day visits cannot be ordered meaningfully                                                                                                                                                | Order by date, then id; show date only                                           | `visitDateTime`, `vetId`, `status`                                                           |
| 5   | Validation errors are strings with JSON paths inside `schemaValidationErrors[].message`, not machine-readable per-field keys                                                                                                                         | Show `detail` + messages in a banner; client-side rules prevent most 400s        | `errors: { field: code }` (RFC 9457 extension)                                               |
| 6   | **No optimistic concurrency on writes.** `ETag` exists only on GET responses for HTTP caching (304); `PUT` does not accept `If-Match` → two receptionists editing the same record = silent last-write-wins                                           | Client-side conflict check before saving (best-effort, not atomic)               | `PUT` with `If-Match` → `412 Precondition Failed`                                            |
| 7   | The same resources are reachable through **two route families** (`/pets`, `/visits` and owner-scoped `/owners/{o}/pets/{p}/…`) with no stated canonical one, so clients can write inconsistent data through either                                   | Use owner-scoped routes only                                                     | One canonical path per resource                                                              |
| 8   | Security is **off by default** and the demo user is `admin/admin`                                                                                                                                                                                    | Out of scope; no auth UI                                                         | Auth on by default in non-dev profiles                                                       |

_Correction history:_ an earlier draft of this README said `PUT` returns 204 and that error bodies are inconsistent; the spec says `PUT` returns 200 + the resource and errors use `ProblemDetail`. The client accepts any 2xx for writes and reads `ProblemDetail`. An earlier client also sent `id` in the `PUT /pets/{id}` body; the spec's request schema (`PetFields`) has no `id`, so it was removed and a contract test now pins the exact body fields of every write call.
